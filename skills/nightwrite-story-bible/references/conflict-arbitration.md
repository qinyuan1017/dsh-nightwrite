# 账本冲突的仲裁顺序

SKILL.md 第 5 步要求「回执里写清改了什么、为什么改、影响哪几回」，但没说**冲突时谁是基准**。这份给完整的优先级顺序、七个常见仲裁场景、以及每种仲裁的代价。

---

## 一、六级优先级（从上到下）

冲突时，**上一级覆盖下一级**。

| 级 | 来源 | 说明 |
|---|---|---|
| **L1** | 已发布正文 | 读者已经读过的东西。改它 = 承认错误，代价最高 |
| **L2** | 已 `accepted` 的章节 | 系统内已验收。改它需要重开验收 |
| **L3** | 账本明文条目 | 作者的正式承诺 |
| **L4** | 细纲（`outline`） | 计划，可以改 |
| **L5** | 未定稿正文（draft） | 草稿，随便改 |
| **L6** | 对话中的口头约定 | 最弱，只作参考 |

### 为什么正文高于账本

因为**读者只知道正文**。账本写「他左手断了」，正文写「他左手握手」，读者读到的是「作者搞错了」——不管账本怎么记。

**但有一条例外**：如果账本条目 `updatedAt` **早于**该章正文的创建时间，且正文与该条目冲突，则说明是**写手写的时候没查账**。此时仍以正文为 L1，但要在回执里记「账本条目 X 早于本回，本轮未生效，建议补一句正文圆场」。

## 二、同级的仲裁规则

### 同类内部冲突

两条 `characters` 都写了同一个人的身份，且不同：

| 规则 | 判法 |
|---|---|
| 更晚 `updatedAt` 优先 | 但不是绝对——要看改动理由 |
| 更具体优先 | 「陈留县仵作」胜过「仵作」 |
| 若两条都具体且不同 → **不能自动仲裁**，必须回作者确认 |

**「必须回作者确认」是允许的**，不属于「视情况而定」。这是明确的动作：**报告冲突，不自行选一个。**

### 跨类冲突

`characters.threshold` 与 `rules.forbid` 打架（规则禁止的事，人物的阈值里没禁）：

- **`rules` 胜**。世界规则高于个人习惯。
- 修法：在 `threshold` 里补一条，或给这个人一个「不知此规」的状态。

`locations.relation` 与 `conflicts.stake` 打架（地理关系说 A 依赖 B，冲突说 A 可以不顾 B）：

- **`conflicts` 胜**。冲突是剧情当下的张力，地理关系是背景。
- 修法：把 `locations.relation` 改成「曾经依赖，现已……」并注明变化回号。

## 三、七种常见仲裁场景

### 场景 1：正文与账本明文冲突，正文已发布

**仲裁**：正文 L1 胜。

**处理**：
1. 改账本，`updatedAt` 更新。
2. 回执写「账本原值 X，因第 N 回正文 Y，修正为 Y」。
3. 影响评估：这条改动会不会影响后文已排的细纲？会 → 列出需重排的回。

**代价**：账本的权威性降低一档。同一类错误出现 ≥3 次，说明账本维护流程有问题，要在报告里点名。

### 场景 2：正文与账本明文冲突，正文是草稿

**仲裁**：账本 L3 胜。

**处理**：改草稿，不改账本。

### 场景 3：账本自相矛盾（两条都具体）

**仲裁**：**不仲裁**，报告冲突。

**处理**：
1. 列出两条的 `id`、`name`、冲突字段、`updatedAt`。
2. 写「需作者确认以哪条为准」。
3. 在冲突解决前，**这一条相关的正文判据全部降级为警告**（不许判致命，因为基准不明）。

### 场景 4：细纲与已写正文冲突

**仲裁**：正文 L1/L2 胜。

**处理**：改细纲。回执写「细纲第 N 回原定 X，因正文已写 Y，重排为……」并列出连锁影响。

### 场景 5：伏笔 `payoffAt` 早于当前进度但未收

**这不是账本冲突，是伏笔断线**。走 `nightwrite-continuity-pass` 的 `foreshadow-break-criteria.md`。

账本侧只做一件事：**不许偷偷把 `payoffAt` 往后改来「消除」超期**。改 `payoffAt` 必须在回执里明写「超期调整，原定 N 回，改为 M 回，理由……」

### 场景 6：`terms` 同一物件两种写法

**仲裁**：`firstAt` 更早的胜。

**处理**：
1. 保留先出现的写法为 `name`。
2. 后出现的写法建为**别名条目**（`definition` 写「即『X』」）。
3. 若后出现的写法已在 ≥3 回正文用过 → 反向：以出现次数多的为 `name`，早期那一回列为「需修正的旧写法」。

**判据**：**以「读者已经习惯的」为准**，不以「作者觉得更好的」为准。

### 场景 7：`characters.state` 与正文的知情状态冲突

**仲裁**：正文胜，且必须**立刻**更新 `state`。

**这是最紧急的一类**。`state` 不更新会导致后续每一章都判不准。规则：**发现 `state` 落后于正文，不论本次任务是什么，先补 `state`。**

## 四、仲裁的三个不许

### 不许 1：不许为了省事选「好改的那边」

仲裁依据是优先级，不是工作量。**「正文改起来麻烦所以改账本」是错的**——那是把读者已经读到的东西作废。

### 不许 2：不许静默仲裁

所有仲裁都必须在回执里写明：冲突双方、依据的优先级、选择了谁、影响哪几回。**静默改账 = 账本失信。**

### 不许 3：不许用「以后再统一」

发现冲突必须当轮处理。挂着的冲突会在下一章变成第二个冲突。

---

## 五、仲裁后的连锁检查

仲裁完一处，必须查三处：

1. **同类：** 同一类里有没有别的条目也在同一个点上错了？（例如身份错了一处，往往错了一批）
2. **引用方：** 有哪些条目引用了被改的这条？它们要不要跟着改？
3. **已写章：** 被改的这条，在已写正文里出现过几次？每次都能自洽吗？

**第 3 项最容易漏**。判据：用 `name` 的关键词搜全部已写章，逐处比对。

---

## 六、回执的冲突记录格式

```
【账本冲突检查】
  冲突：有
  - A 方：characters/沈砚.identity = "陈留县仵作"（updatedAt 2026-09-12）
  - B 方：第 14 回正文「他早就不当仵作了」
  - 仲裁：正文 L1 胜 → 改账本
  - 改动：identity → "陈留县仵作（第 14 回起已辞）"
  - 影响回目：第 14 回（已写，无需改）；第 18 / 22 回细纲需检查是否仍假定他在职
  - 连锁：characters/二叔.state 记「使唤沈砚验尸」→ 需改为「曾使唤」
```

**必须有的五项**：冲突双方、依据、改动、影响回目、连锁检查。

---

## 七、预防性措施

减少仲裁的四条：

1. **`state` 每章写完后更新**。这是最高性价比的一条——多数冲突源于 `state` 落后。
2. **`terms` 首次出现即登记**。不要等「以后统一」，那时已经写歪了。
3. **`threshold` 必带破例条件**。没有破例条件的阈值遇到剧情需要必然被破，破了就是冲突。
4. **细纲里出现账本没有的东西，先补账再写正文**。写手最常见的顺序错误：先写正文，事后补账——补出来的账一定是「圆场账」，不是「基准账」。
