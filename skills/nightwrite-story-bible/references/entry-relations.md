> 适用：建完条目之后要查「这张账本是不是一坨散沙」时读这份；判「这条设置有没有真正接进剧情」时读这份。

# 条目之间的引用关系

账本的价值不在条目数，在**引用密度**。一条 `rules` 如果没有任何 `characters.threshold` 指向它、没有任何 `events` 用到它，那它在写作时永远不会被调用——等于没设。

---

## 一、八类的引用图

```
        ┌────────────┐
        │ characters │◄──────────┐
        └─────┬──────┘           │
              │ threshold/goal   │ between/who
              ▼                  │
        ┌────────────┐     ┌─────┴────┐
        │   rules    │     │conflicts │
        └─────┬──────┘     └─────┬────┘
              │ cost             │ stake
              ▼                  ▼
        ┌────────────┐     ┌────────────┐
        │   events   │◄────┤ locations  │
        └─────┬──────┘     └────────────┘
              │ at
              ▼
        ┌────────────┐
        │ foreshadow │
        └─────┬──────┘
              │ name ← 正文物件
              ▼
        ┌────────────┐
        │   terms    │
        └────────────┘

        ┌────────────┐
        │ highlights │  （旁挂：被 events 复用，不反向引用）
        └────────────┘
```

### 箭头的含义

`A → B` 表示「A 的某个字段的值必须是 B 里已存在的条目」。**建条目时，每个箭头都要落地，否则是断链。**

---

## 二、五个必须落地的箭头

### 箭头 1：`events.who` → `characters.name`

**判据**：`events` 里 `who` 列出的每一个名字，`characters` 里必须有同名条目。

**不落地的后果**：一个在事件里做了关键动作的人，账本里没有他的阈值和状态，后面写他做事时无法判越界。

**修法**：要么给他建卡，要么把他从 `who` 里删掉（说明他其实不重要）。

### 箭头 2：`events.at` → `locations.name`

**判据**：每个事件的地点必须在 `locations` 里。

**不落地的后果**：无法判地理冲突（一个人不可能同时在两地）。

### 箭头 3：`foreshadow.plantedAt/payoffAt` → 具体回号 → 该回的 `events`

**判据**：伏笔的埋设回和回收回，都应该有至少一个 `events` 条目。

**不落地的后果**：伏笔变成「作者备忘」，而不是「剧情的一部分」。这种伏笔最容易断——因为它不在事件链上，写手不会想到它。

### 箭头 4：`characters.threshold` → `rules`

**判据**：如果阈值来自某条世界规则（「仵作不验自家人」来自行业规矩），这条规矩应该在 `rules` 里。

**不落地的后果**：阈值变成「这个人的性格」，可以被剧情需要推翻；落地了就是「这个世界的规矩」，推翻需要代价。

### 箭头 5：`conflicts.between` → `characters`

**判据**：冲突双方必须都有卡。

**不落地的后果**：冲突的一方是「反派」这种空壳，写起来只会功能化。

---

## 三、三个可选箭头（有则更好）

### 箭头 6：`terms` → `characters`（谁持有）

物件类专名应能指向持有者。写在 `definition` 的括号里：
> 「玄铁令（黑铁，三寸）【第 9 回起由二叔持有】」

### 箭头 7：`highlights` → `events`（从哪个事件抽象出来）

`highlights` 的 `at` 应指向一个 `events`。这样高光不是凭空的，是「这个事件的结构值得复用」。

### 箭头 8：`locations.relation` → `locations`

地理之间的关系必须成对出现，方向相反：
> A 的 `relation`：「A 怕 B，因为……」
> B 的 `relation` 里必须有对应的「B 拿住 A 的把柄」

**只写一边 = 关系不完整。**

---

## 四、引用密度的量化

```
引用密度 = 入向引用总数 ÷ 条目总数
```

「入向引用」= 有多少其他条目引用了它。

| 密度 | 判定 |
|---|---|
| <0.5 | 账本是散沙，条目大多没接进剧情 |
| 0.5–1.0 | 及格 |
| 1.0–2.0 | 良好，账本在起作用 |
| >2.0 | 枢纽型条目多（核心人物/核心规则），正常 |

### 计算示例

```
characters 12 条，入向引用：events.who 引用 34 次 + conflicts.between 引用 6 次 = 40
  → 平均每条 3.3 次（良好）

rules 5 条，入向引用：threshold 提到 2 次 + events 用到 1 次 = 3
  → 平均每条 0.6 次（偏低，规则基本没进剧情）

terms 20 条，入向引用：0
  → 0（这些专名只是词典，没接进任何地方）
```

**`terms` 的引用密度天然低**（专名是被正文引用的，不是被账本引用的），所以 `terms` 不计入这个指标。

---

## 五、三类断链的诊断

### 断链 1：孤儿规则

`rules` 里没有任何条目引用它。

**判据**：这条规则在剧情里永远不会被触发 → 它是设定，不是规则。

**修法**（三选一）：
- 给一个角色的 `threshold` 挂上它
- 排一个 `events` 用到它
- 删掉（因为用不到）

**不许**留着「以后可能用」——这正是账本膨胀的原因。

### 断链 2：幽灵人物

`characters` 里存在，但 `events.who` 从未出现。

**判据**：这个人从没在事件里做过事 → 他不参与剧情。

**修法**：要么给他排事件，要么标为「背景人物」（在 `identity` 里加「背景」前缀，不参与判定）。

### 断链 3：悬空伏笔

`foreshadow` 的 `plantedAt` 指向的回，`events` 里没有任何事件。

**判据**：这个伏笔埋在一个「什么也没发生」的回里 → 读者不会注意到。

**修法**：把埋设点挪到一个有事件支撑的回里，或给那一回补事件。

---

## 六、双向一致性检查

有些引用必须双向对得上。三个必须查的：

### 检查 1：师徒/血亲关系

`characters` A 的 `identity` 写「某某的徒弟」，B 的 `identity`/`state` 里必须有「收了 A」。

**不对等的后果**：写 B 时不会想到 A，A 就变成孤儿。

### 检查 2：地理控制权

`locations` A 的 `controller` 写「归 X」，`characters` X 的 `state` 里应记「控制 A」。

### 检查 3：冲突的输赢后果

`conflicts` 的 `stake` 写「沈砚输 → 失去族籍」，`characters` 沈砚的 `threshold` 里应有「不让人夺走族籍」这类对应。

**不对等的后果**：赌注和人物动机脱钩，读者会觉得「他好像也不是很在乎」。

---

## 七、建账的推荐顺序

新建一本账时，按这个顺序建能让引用自然落地：

1. **`rules`** —— 先定世界的物理与代价
2. **`locations`** —— 再定舞台与距离
3. **`characters`** —— 人物挂在规则与地点上（阈值取自 `rules`，位置取自 `locations`）
4. **`conflicts`** —— 冲突由两个 `characters` 的不兼容目标生成
5. **`events`** —— 事件由冲突推进
6. **`foreshadow`** —— 伏笔埋在事件里
7. **`terms`** —— 专名在事件里首次出现时登记
8. **`highlights`** —— 写完一卷后回过头抽象

**倒序建的后果**：先建 `characters` 再建 `rules`，会导致人物阈值与规则打架；先建 `terms` 再建 `events`，会造出一堆用不上的名词。

---

## 八、回执里怎么写引用

`ledger.upsert` 的回执中，`【账本冲突检查】` 一栏应包含引用检查：

```
【账本冲突检查】
  重复：无
  引用：events.who 里的「二叔」「阿禾」均已有 characters 条目
        foreshadow.payoffAt=11 对应 events「祠堂夜审」（第 11 回）
  断链：术语「玄铁令」首次出现于第 4 回，但 terms 未登记 → 待补
```

**「待补」是允许的**，但必须在同一轮补完，不许跨轮挂着。
